# 可行性評估：塔麻可吉主題互動電商前台

依據：`ideation/intent-capture/intent-statement.md`（意圖聲明）、`feasibility-questions.md`（Q1–Q11），以及對現有 `inventrix-code/` 的盤點。

## 結論

**有條件可行。** 技術上沒有做不到的部分，但「1.5 小時內成果發表」（Q6）無法同時容納意圖聲明的完整範圍。你已選擇時程優先（Q11），因此可行的前提是：在「範圍定義」階段大幅縮減基礎設施與互動範圍。

| 面向 | 判斷 | 理由 |
|------|------|------|
| 前台改造（吉祥物、像素風、動畫音效） | 可行 | 現有前台為 Vite + React + TypeScript，團隊熟悉（Q9）；屬純前端工作 |
| 便便點數兌換 | 可行 | 只用遊戲內點數、不涉及真實金額（Q2），不必串金流；需新增點數餘額與扣點邏輯 |
| SQLite 改為 RDS PostgreSQL | 可行，中等工作量 | 現用 `better-sqlite3` 同步 API，約 30 處查詢要改成非同步並調整 SQL 語法（自動遞增欄位、日期型別） |
| 多可用區、容器、負載平衡 | 技術可行，時程不可行 | 團隊熟悉 AWS 容器與 CI/CD（Q9），但多可用區資料庫、容器叢集、負載平衡的建立與除錯時間難以塞進 1.5 小時（估計，未經實測） |
| CodePipeline／CodeBuild（GitHub 來源） | 技術可行，時程風險高 | 需先建立 GitHub 連線與管線，第一次部署常需多次修正（估計） |
| 走完 mvp 流程剩餘 18 個審核點 | 時程風險高 | 每個階段都需要你的回答與核准 |

## 技術觀察（現有程式碼）

- 後端約 475 行，規模小，改造成本低。
- 商品圖片存在伺服器本機 `public/` 資料夾；多個容器同時運行時，各容器看不到彼此的檔案，要嘛改放共用儲存，要嘛示範時不產生新圖片。
- 商品圖片產生功能依賴 Amazon Bedrock。
- 資料庫初始化時寫入固定的管理員與顧客密碼；目前只用假資料（Q8），示範可接受，但不可沿用到正式環境。
- 專案目錄內有 `inventrix-key.pem`（EC2 金鑰）。程式碼要放上 GitHub（Q4），這個檔案絕不能被提交。
- 本機專案目錄不是 git repository，與 GitHub repo `chaoting-sun/inventrix` 的對應關係尚未確認。

## 建議

- 範圍定義時以「1.5 小時內可展示」為硬性條件，排出必做與延後清單。
- 基礎設施先做「設計上可擴展」的最小可運行版本，多可用區與完整 CI/CD 列為延後項目，或在時程內只做其中一項。
- 考慮是否換成步驟較少的流程，以減少審核點佔用的時間（是否調整由你決定）。
